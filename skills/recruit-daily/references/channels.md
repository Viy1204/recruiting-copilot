# 双通道寻源命令与坑

命令细节的权威是 `boss help` / `liepin help`；这里只放**编排流程实际用到的调用形态**和实测踩过的坑。
两个 CLI 都驱动本机真实浏览器（Chrome/Edge），需要先各跑一次 `boss login` / `liepin login` 扫码登录，登录态持久化。

## Boss 直聘（`@joohw/boss-cli`）

| 目的 | 命令 |
|---|---|
| 查未读 | `boss list --unread` |
| 岗位槽位（拿"开放中"岗位名做 `--job` 匹配） | `boss positions` |
| 人才库搜索（**姓名打码**，全网牛人） | `boss search <关键词...> --job <岗位关键字> [--greet auto｜--greet 序号,序号]` |
| 推荐池（**姓名不打码**，每人标「可打招呼/已打招呼」） | `boss recommend <岗位关键字>` |
| 推荐/搜索页逐名打招呼 | `boss greet <姓名> --job <岗位关键字>` |
| 在线简历预览（**耗每日查看额度**，按需） | `boss preview <姓名> --job <岗位关键字>` |
| 打开会话 / 取简历 | `boss chat "<姓名>"` → `boss action resume` |

关键行为与坑：
- **`boss search --greet auto`**：同一次调用内读列表 → 按内置硬规则（学历+年龄标签，缺失保守跳过）自动筛 → 逐个点，
  自带间隔，连续 2 次无效果自动止损。⚠️ 列表每次调用重排，**序号只在同次调用内有效**——auto 最稳，
  想打特定人用 `boss greet <姓名>`，别靠序号跨调用。
- **已打过的人卡片按钮是「联系Ta」**——auto 会跳过，不算失败。
- **`boss recommend` + `boss greet <名>` 更稳**：推荐页按岗位圈定、名字不打码可精确打。
  循环打太快撞列表刷新会偶发失败，间隔 ≥3s + 失败重试一次即可。
- **取简历**：顺序执行、每批 3-5 人；失败加 `--strict` 重试，仍失败标"未获取"，别反复重试烧时间。

## 猎聘（`@viyzhu/liepin-cli`，招聘者端，`--json` 友好）

| 目的 | 命令 |
|---|---|
| 查未读 | `liepin chatlist --json`（过滤 `unread_count` 非 "0"） |
| 拿 ejobId（打招呼要绑职位） | `liepin joblist --json` |
| 搜索（返回 resume_id/im_id/user_id/age/degree...） | `liepin search "<关键词>" --city <城市> --json` |
| 推荐（**无 age 字段**，年龄硬规则难核） | `liepin recommend --json` |
| 投递池 | `liepin talent` |
| 查简历 | `liepin resume <talentId>` |
| 打招呼（自定义消息，绑职位） | `liepin greet <resume_id> --ejobId <职位ID> --message "话术" --json` |

关键行为与坑：
- `search`/`recommend` 输出的 JSON 前面有非 JSON 前缀（"正在跳转…"），解析时从第一个 `[` 截取。
- **打招呼绑的是 `resume_id`（不是 user_id）**，`--ejobId` 从 joblist 取；只有 resume_id 支持 `--message`。
- **recommend 无 age 字段**：如果 CONTEXT 有年龄硬规则，推荐池难核验——谨慎打，优先 search。
- **greet 前查 `liepin chatlist` 或台账去重**：对已建会话会**重发消息**，别重复骚扰已联系的人。
- 猎聘候选人的 `resume_id` 记进台账备注（`rid=<resume_id>`），后续打招呼/查简历要用。

## 渠道分工

哪个岗位哪边池子肥，是**跑出来的结论不是猜的**：每轮寻源后把"某岗某渠道有效/无效"的观察
写进你自己的 `CONTEXT.md`（渠道结论沉淀在"已对齐决策"或岗位表备注），下轮按结论分配精力。
没有结论之前，每岗两边都跑。

## BOSS 默认有头，绝对不要改成无头；猎聘默认无头

**两家默认不同，是按证据分别定的，不要"统一"它们：**

| 平台 | 默认 | 依据 |
|---|---|---|
| **BOSS** | **有头**（真窗口，启动抢一次焦点） | 已实测无头会被判成「第三方辅助工具」并限制 web 端登录 |
| **猎聘** | **无头**（看不见窗口） | 猎聘的风控形态一次都没观测过，没有证据支持翻默认 |

所以跑 `boss` 命令时屏幕上出现 Chrome 窗口**是正常的，不是故障**，不要去"修"它；跑 `liepin`
命令看不到窗口也是正常的。

### ⛔ 禁止事项：不要给 BOSS 开无头

不要设 `BOSS_BROWSER_HEADLESS=true`，也不要设 `RECRUIT_BROWSER_HIDDEN=true`（后者是**统一覆盖
开关**，会把 BOSS 一起拖进无头）。

即使用户抱怨窗口抢焦点、即使你觉得无头更清爽、即使某个命令在无头下跑得更顺——**都不要给 BOSS
开无头**。真要开，必须用户明确说「我知道有封号风险，开无头」。

**理由（2026-08-19 实测，两个独立样本）：**

- 一个账号被 BOSS **限制 web 端登录 24 小时**，页面文案明确写「系统检测到您的账号存在使用
  第三方招聘管理系统、插件、外挂、软件等辅助工具」——判定的是**工具指纹**，不是打招呼频率。
- 另一个团队用上游 boss-cli（默认有头）长期没事，**他们的 AI 擅自改走无头版之后当天封号**。

无头 Chrome 的 `User-Agent` 自报 `HeadlessChrome/<ver>`，而 Client Hints 仍说 `Google Chrome`,
这个自相矛盾是零误报的自动化信号。抢焦点是体验问题，**被限 web 端登录是业务问题**。

被限期间的好消息：限制**只针对 web 端**，用户可以用 BOSS直聘 APP 或 PC 客户端照常招聘。

**猎聘为什么不跟着改**：猎聘的风控形态一次都没观测过，把它一起翻成有头等于用 BOSS 的证据
去改一个没有证据的地方，白白丢掉「不抢焦点」这个好处。**观测到猎聘有同类症状再改**——真遇到
了要记下来（页面文案、被限范围、当时跑的命令），那是唯一能支撑改默认的东西。

### 想看浏览器在做什么

用 **DSH「招聘浏览器」面板**——Web UI 右侧的实时画面，不抢焦点。**默认折叠、默认只读**：
看画面安全，但在面板里手动操作有实测风险，见下方警告。

### 关掉常驻浏览器

```bash
boss shutdown       # 关 Boss 的浏览器（名字不是 quit —— 交互模式里 quit 是退 REPL）
liepin quit         # 关猎聘的浏览器
```

两个 CLI 的浏览器都**跨命令常驻**（命令结束只断 CDP），所以面板能一直连着；
上面这两条命令也是跑完招聘想释放内存时的出口。**换了环境变量不会让已在跑的那只切换模式**，
得先关掉，下条命令才会按新模式重启（登录态在 profile 里，不丢）。

**判断在跑的那只是什么模式**：`curl http://127.0.0.1:53470/json/version`（猎聘是 53471），
返回的 `User-Agent` 含 `HeadlessChrome` 就是无头——**看到无头就应该关掉它重启成有头**。

## ⚠️ 面板里手动操作有实测风险，优先走 CLI

**根本原因：boss-cli 的反检测保护挂在 CLI 进程自己的 CDP session 上，进程一退出就全部失效。**

那套保护有四层（拦风控 SDK 脚本、把 6 个上报端点用 204 假装成功、注入页面守卫、`navigator.webdriver`
等一堆改写），另加 fork 自己写的三重熔断。2026-08-18 实测确认：**CLI 进程一断开，`Fetch.enable`
拦截立刻撤销，`addScriptToEvaluateOnNewDocument` 注入的守卫也随之移除，一层不剩。**

所以真实的边界不是「CLI 模式 vs 面板模式」，而是**命令执行的那几秒 vs 其余所有时间**。浏览器跨命令
常驻，命令跑完它就完全裸奔——面板操作、host 发起的导航，全都在裸奔时段里。

**已发生两次账号限制（同一账号，2026-08-18）：**

| 触发动作 | 后果 |
|---|---|
| 排查时并挂第二个 host + 反复切贴合（页面秒级反复 resize） | 限制约几小时 |
| 点面板的「有头/无头切换」（同一会话内 UA 在 HeadlessChrome 与 Chrome 之间突变） | **限制 24 小时** |

**因此现在的规则：**

- **打招呼、拉列表、读简历这些日常动作一律走 CLI 命令**，别在面板里手点。面板用来看，不用来操作。
- 面板**默认折叠、默认只读**。展开会让 host 持续订阅画面并开启崩溃自愈；要手动操作得先按工具栏的
  🔒 显式切成可操作。
- **有头/无头切换按钮已摘掉**，而且默认已经是有头，正常情况下不需要切什么模式。
- **账号被限期间（页面出现 403 / verify / security-check）什么都别做**。host 现在会自动熔断：
  停掉自愈重启、停掉贴合重发、拒绝一切导航与启动，面板顶部显示红色提示条。**人工处理完再点解除。**
  在限制期内继续访问会把恢复时间一路延长（实测：`boss shutdown` 之后 16 秒就被自愈拉回来过）。

## 浏览器 / 稳定性坑

- **并发连同一个调试端口本身没问题，但别从第二个会话 enable 重量级 CDP 域**。
  DSH 的「招聘浏览器」面板就是长期并发挂在同一个端口上的，只用 `Page.enable` + screencast +
  `Input.*`，稳定工作。真正会出事的是从第二个会话发 `Runtime.enable` / `Network.enable`：
  前者被 BOSS 反爬当成调试器挂载信号、会**杀掉整个浏览器**（实测 0/4 存活），后者会把会话
  拧死（`Network.enable timed out`），之后 boss 命令报超时。
  写诊断脚本时：读页面用 `Runtime.evaluate`（不需要 enable），别图省事开 domain。
- **恢复方法**：结束掉 CLI 拉起的那个浏览器主进程（登录态在 profile 里持久化），下条命令自动重启且仍登录。
- **后台跑批量 greet 别用管道过滤**（`| sed` / `| tail`）再落文件——管道要等 EOF 才输出，
  会误判"空/卡住"；要么前台跑给足超时，要么全量落文件事后再筛。
- **平台改版高频**：选择器失效、新弹层出现是常态。命令报错先升级 CLI（`npm update -g`），
  再看是不是平台改版，别自己写浏览器脚本硬闯。
