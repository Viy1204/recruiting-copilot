# 招聘看板：每轮重点与跨轮待确认

日期：2026-11-04

状态：grilling 访谈的 Q1–Q21 已逐项确认，用户于 2026-11-04 确认完整方案并授权实施。源码与隔离数据验收已完成，随后按用户授权接入真实工作区。用户实用反馈要求进一步简化展示，布局和详情交互以 [ADR 0002](../adr/0002-board-progressive-disclosure.md) 为准；本文的跨轮存储、决定与执行语义不变。

## 1. 目标与现状

主动招聘任务和定时巡检都应及时把已经核实的重点反馈到面板。需要用户决定的事项跨轮保留；决定作出后，相关资料更新与后续执行仍有可查看的状态，直到完成、明确取消或失效。

三项验收目标：

- 看得见进展：能区分正在做、已经做、没有重要变化和执行失败。
- 找得到未处理事项：新任务、新会话、应用重启和岗位筛选都不会让未解决事项失去入口。
- 决定能落实：知道用户决定了什么、适用于什么，以及相关动作是否真正完成。

当前源码已确认：

- `run.results` 保存本轮逐人结果；首页确认名单跟随所选 run。换轮不会删除旧文件，但缺少跨轮未解决事项汇总。
- 终态 run 保留结果，但拒绝后续更新，不能承担独立于原任务结束时间的决定处理。
- 网页已有前台约 1 秒轮询，原生约 2 秒；存在历史选择和阅读位置保持能力。刷新不是任务存活证明。
- 结果由工作流显式记录，不会自动从聊天全文提取；未核查实际安装副本及现有定时巡检的调用入口。
- 项目以用户工作区的 `CONTEXT.md` 为岗位标准事实源，台账与候选档案保留各自职责。看板不另建候选数据库，不通过网页执行招聘平台动作。

相关依据：

- [首屏减负设计](recruit-board-focus.md)：原有“不引入跨轮待办”的范围限制将由本次新决策正式调整。
- [项目设计](../DESIGN.md)：本地文本、跨宿主、岗位标准唯一事实源和平台操作边界。
- [共享进度协议](../../skills/recruit-board/references/progress.md)：轮次、结果、终态、读数与工作流记录规则。
- [宿主接入](../../skills/recruit-board/references/hosts.md)：网页主入口、原生可选入口、服务生命周期与降级。

## 2. 已确认的设计树

```text
每轮任务与面板联动
├─ 重点反馈
│  ├─ 信息范围：影响下一步行动的事实（Q1）
│  ├─ 更新时机：执行中及时更新，结束后汇总（Q2）
│  ├─ 无变化轮次：更新任务状态，保留近期重要进展（Q12）
│  ├─ 信息层级：状态 → 待你确认 → 近期重点 → 岗位与人选（Q13）
│  └─ 多轮并存：保持阅读位置，提示其他轮次的新进展（Q14）
├─ 跨轮待确认
│  ├─ 准入：必须由用户拍板、授权或补充关键信息（Q3）
│  ├─ 范围：同一工作区全轮次可见（Q5）
│  ├─ 合并：同一对象、决定与适用范围合并（Q6）
│  ├─ 退出：明确处理、取消或有据失效（Q7）
│  ├─ 暂缓：持续可查，降低重复提醒（Q9）
│  └─ 旧数据：历史待核对，不能把旧标记当作当前事实（Q15）
├─ 决定与落实
│  ├─ 入口：聊天作决定，面板同步（Q4）
│  ├─ 状态：决定和执行分别记录（Q8）
│  ├─ 阻塞：只暂停依赖该决定的动作（Q10）
│  ├─ 当场执行：有条件且已授权时继续落实（Q11）
│  ├─ 修订：保留历史，旧任务不能覆盖新决定（Q16）
│  ├─ 续办：后续任务检查并续办，先核实是否已完成（Q17）
│  └─ 事实源：相关标准、台账或档案同步更新（Q20）
└─ 可用性与交付
   ├─ 到期提醒：面板与任务摘要，重新打开时补上（Q18）
   ├─ 故障反馈：保留最后可信状态，不把未知显示成零（Q19）
   └─ 范围：六个工作流、主动与定时执行、网页与原生（Q21）
```

## 3. 面板呈现

| 区域 | 默认呈现 | 可展开内容 |
|---|---|---|
| 任务状态 | 当前任务及最近结束任务的简短状态、时间、主动或定时来源；无变化仍有完成记录 | 各轮进度、失败或阻塞原因、执行记录 |
| 待你确认 | 固定入口与未解决总数，优先显示 3 项需要当前处理的事项 | 全部待确认、已暂缓、历史待核对、处理历史 |
| 后续执行 | 待你确认区域内保留独立入口及数量，区分待执行、执行失败、资料待同步 | 已作出的决定、动作范围、当前原因、完成证据 |
| 近期重点 | 少量有价值的最新进展，标注时间与来源轮次 | 依据、相关事项或人选、每轮摘要及详细记录 |
| 岗位与人选 | 保留现有搜索、筛选、阶段、资料和岗位管理 | 现有候选详情及档案入口 |

数量语义必须明确：

- “待你确认”的未解决总数包含当前待处理和已暂缓，分组展示各自数量；不能把暂缓写成已完成。
- “历史待核对”单列，不冒充已证实仍有效的当前待办。
- 已明确决定且无需再次回答的事项转入后续执行，不继续计入“待你确认”；执行失败仍可查。
- 需要重新授权或重新决定时，才重新进入待确认，并说明原因。
- 岗位、人选及当前轮次筛选不隐藏固定入口的工作区总数；可在展开列表内主动筛选。

待确认按明确截止时间、是否阻塞后续动作、首次提出时间排序。已暂缓事项默认不占用前三条。没有真实截止时间就不制造逾期判断。

阅读历史、依据、人选详情或编辑岗位时不强制导航、不重置滚动位置；其他任务产生更新时给提示。回到默认总览后汇总各轮重点，注明来源，避免把后台巡检误称为当前聊天任务。

## 4. 每轮重点的生成与更新

工作流在事实核实后显式记录，面板负责展示与同步。普通日志、计划和未验证的动作不能自动升格成成功结果。

重点包括：

1. 值得进一步关注的人选及简短理由。
2. 已完成的关键动作及实际结果。
3. 需要用户决定的事项及新增依据。
4. 任务异常、受阻或关键执行失败。

每条重点保留短结论、事件时间、关联对象、来源 run、可查看的依据以及必要的关联事项。普通候选跟进属于候选进展；除非确实需要用户判断，不进入长期待确认。

- 执行中及时写入已核实进展；结束时形成该轮摘要。
- 明确区分“进行中”“已完成”“失败”“无重要变化”和“未记录／无法读取”。
- 同一对象同一事件的后续进展更新或关联原事件；不同事件不能仅凭同名合并。
- 无变化巡检更新最近任务状态，不覆盖上一条仍有展示价值的重要进展。
- 同一事项没有新事实时，不在每轮重点里重复生成一条相同提醒。
- 重要结果被纠正时保留更正信息，不能继续把过时结论当作当前事实。
- 快照仍保持轻量，详情按需读取；不把整份简历、联系方式或聊天全文塞入动态摘要。

实现默认值：近期重点首屏 3 条，默认“近期”取最近 7 天，可进入历史查看各轮记录。7 天只控制首页重点窗口，不限制事项保留期，也不删除历史。该窗口是可调整的呈现默认值。

## 5. 待确认事项的独立生命周期

事项不再依附于某一轮是否仍在运行。一个事项可以关联多个发现轮次、证据和处理轮次。

| 状态或阶段 | 含义与后续 |
|---|---|
| 待确认 | 用户尚未作出明确且可对应的决定 |
| 已暂缓 | 仍未解决，保留入口；到期或出现重要新情况时恢复提醒 |
| 已决定 | 记录答复、适用范围和必要依据；如果有后续动作，进入后续执行 |
| 后续待执行／执行中 | 用户不需要重复回答，等待资料同步或已授权动作落实 |
| 执行失败／结果待核实 | 保留原因和真实状态，不能声称成功，也不能盲目重试 |
| 已完成 | 无需后续动作，或所需资料更新与动作均已确认完成 |
| 已取消／已失效 | 明确取消或有证据证明无需继续，保留原因供回查 |
| 历史待核对 | 旧记录曾标注待确认，但尚不能确定当前是否仍需处理 |

“决定状态”和“执行状态”分别记录，上表是用户可以理解的阶段，不要求把二者挤进一个互斥字段。一个决定关联多项动作时分别记录结果，不能把一项成功当成全部完成。

### 识别与合并

- 合并依据为同一对象、同一个决定及相同适用范围。事项保留稳定标识，不用每轮随机生成新事项替代旧事项。
- 岗位规则、单个人选的例外、单次外部动作授权分别记录适用范围。
- 复用能证实对应关系的岗位或台账标识；姓名、近似措辞或相似简历本身不能证明同一事项。无法确定时保持独立，不强行合并。
- 多轮发现合并来源引用及证据，保留首次提出和最近更新；重试同一写入不会重复增加事项或历史事件。
- 跨工作区不合并，避免不同招聘项目互相影响。

### 退出、暂缓与重开

- 换轮、会话结束、应用重启、长期未回复和未选中岗位都不是关闭事项的理由。
- 明确拒绝也属于已作决定，记录结论；不能让被拒绝的动作继续等待执行。
- 明确岗位关闭、候选退出等事实可以使相关事项失效；文件缺失、读取失败或未检索到不是失效证据。只处理确实受该事实影响的事项。
- “下周再看”等明确日期按用户工作区时区转换为可核查日期；“先放着”不擅自生成期限。
- 到期只恢复提醒，不自动变成批准。应用关闭期间不保证主动通知，下次打开或任务运行时补上。
- 用户明确修订决定时保留前后记录、范围和原因；旧任务携带的旧状态不能覆盖最新决定。
- 重要新证据可以重新提请确认，必须说明重开原因；系统不能自行把旧批准或拒绝反转。
- 回看历史轮次时分别呈现“本轮当时提出了什么”和“关联事项现在如何”，不篡改已结束轮次来伪造过去。

## 6. 聊天决定、资料同步与执行续办

聊天仍是主要决策入口。用户无需记事项编号；系统依据当前对话、对象、事项和范围定位，必要时只追问最小的消歧问题。“都同意”只能对应已明确列出的事项集合，不扩展到未展示或无关事项。

答复处理链路：

```text
明确答复并定位事项
  → 记录决定与适用范围
  → 更新相关事实源（如有）
  → 落实当场可执行且已授权的动作
  → 记录真实完成、失败或待续办状态
```

- 普通聊天中的补充决定也能更新事项，不要求原 run 仍在运行，不为了确认而伪造一次完整招聘任务。
- 岗位标准仍以工作区 `CONTEXT.md` 及既有项目约定为准；事项记录保存决定与同步状态，不成为第二套竞争的岗位标准。
- 候选人处理结果按原规则同步台账／档案；仅单人例外不能修改整个岗位标准。
- 涉及多处更新时保留各部分的实际结果。决定已保存但岗位资料未更新，要显示“资料待同步”，不能宣称规则已生效。
- 未确认只阻塞依赖该决定的动作，其他已授权工作继续；本轮可以结束并保留待决定、待执行数量和链接。
- 下一轮先读取相关未解决事项、有效决定及待执行动作；能在授权有效且条件适用时续办。
- 执行前核实是否已经完成。请求超时、网络中断等造成结果不确定时先查实际状态，不盲目重复联系或建会。
- 授权遵守原有对象、范围和有效期。接受异地不等于授权联系所有异地候选人；只读巡检不会因存在待执行动作升级为可外发任务。
- 已获授权且已经完成的动作无需再次授权；授权过期、范围变化或条件实质变化时重新确认，并保留原因。
- 标准修订用于后续相关工作；不能据此悄悄重跑所有历史人选或把过往记录改写成新标准下的判断。

## 7. 持久化、并发与故障处理

沿用本地文件和现有脚本，不增加独立数据库、账号系统或常驻调度服务。

实施方向：

- 保留现有 run 文件及终态边界，为跨轮事项增加工作区级持久化记录，记录决定、动作、变更历史及来源引用。
- 一轮的结果可以关联事项；已结束轮次无须重新打开，事项仍可继续处理。
- 读数与状态变更尽量共用模型和脚本，网页与原生使用同一语义，避免分别维护两套事项状态。
- 复用原子写入、显式锁等现有能力，并增加基于记录版本的过期更新检查；并发写入冲突明确反馈，不能最后写入者静默覆盖新决定。
- 跨文件更新不假装是一次整体成功；以可恢复的处理状态标出已完成与未完成部分，重试应避免重复副作用。
- 只保存必要的决定、证据引用及来源，不抓取宿主私有聊天日志来补造记录。

面板与工作流必须分别反映故障：

- 读取失败：已有内容保留为“最后成功读取”，标明时间及异常；没有可信缓存则显示未知。
- 决定写入失败：聊天明确说明同步未完成；仅当渠道仍可用时显示对应提示，不能承诺已断开的面板知道尚未写入的内容。
- 事实源同步失败：决定仍可保存，但后续状态标明未同步，依赖该更新的动作等待处理。
- 进度服务故障不自动阻断无关的招聘工作；不能可靠核实授权或决定状态的依赖动作须等待。
- 恢复后重新读取、核对与续办，不把连接恢复当成业务动作完成，也不按超时猜任务成功。

## 8. 历史接入与兼容

- 新机制接入后，新事项使用稳定标识及独立生命周期。
- 历史 `attention=decision` 记录先评估来源与可对应的处理证据。有明确处理证据的按证据归档，否则进入“历史待核对”。
- 历史引入保留原 run、收据和时间；重复执行导入不生成重复记录，不直接改写旧 run。
- 核对后转为有效待确认、已处理、已取消或已失效；不因某个候选后来出现在台账就推断原问题已被回答。
- 工作区原有“待定决策清单”等资料是核对依据；本次不静默把所有零散文本都转换成正式待办。只有明确识别、可追溯的事项才登记。
- 旧 run、旧工作区缺少新字段或新文件时保留历史查看能力，区分“尚未接入”“未记录”和“没有事项”。
- 未接入的任务要能看出“本轮未记录重点／事项”，不能把缺记录包装成“无重要变化”。

## 9. 实施范围与依赖顺序

这是一个需要统一落地的改动，底层状态、工作流写入与两个界面不能各自采用不同定义。

1. 新增 ADR，说明跨轮事项独立于 run 的理由，正式调整旧首屏设计的范围边界，同时保留历史设计记录。
2. 完成共享模型、工作区文件存储、事项命令、重点读写及历史兼容，建立生命周期和并发公共行为测试。
3. 更新共享进度说明及六个执行工作流的接入契约；补充工作区路由，使普通聊天确认也能处理已存在事项。
4. 更新网页与原生：固定入口、分组计数、近期重点、后续执行、处理历史、来源标注、阅读保持和故障状态。
5. 在隔离的虚构工作区完成端到端验证；按现有安装与工作区注册测试验证分发兼容，交付变更和验收记录。

六个入口为 `recruit-init / recruit-grill / recruit-daily / resume-review / interview-schedule / market-talent-mapping`。初始化只有工作区实际建立后记录；指南路由或纯查看不创建假任务。

主动／定时是任务触发来源，不是两套工作流。按实际已知来源记录，未知时不猜测宿主或会话绑定。定时提示词必须调用共享入口才能产生这套结果；实际巡检是否如此属于部署阶段必须验证的接入事实，不能靠网页刷新自动保证。

本次实施交付源码、协议说明、自动化测试和虚构数据验收。真实工作区更新、历史数据接入和既有定时提示词核验单独交接；不在源码仓库存放用户岗位或候选数据。当前既有未提交改动保留；未获请求不提交或推送。

## 10. 验收场景

以下全部使用虚构岗位、人选与本地测试动作；验证状态联动不需要向真实候选人发送消息。

| 场景 | 必须观察到的结果 |
|---|---|
| 主动任务执行中产生重点，随后完成 | 核实后及时出现，计划不显示成完成；结束摘要与真实动作一致 |
| 后续多轮巡检均无变化 | 最近巡检时间与状态更新，近期有价值重点仍保留，可回看每轮 |
| 同一待确认事项连续五轮发现 | 只有一个事项，多轮来源可回查，首次提出时间不丢失 |
| 新任务、新会话、重启、岗位切换 | 有效未解决事项始终可从固定入口找到，工作区总数语义一致 |
| 两个人同名、岗位别名变化、相近问题 | 不错误合并或错误消解，无法证实同一性时保留独立记录 |
| 原 run 已完成，用户在普通聊天里答复 | 事项可更新，旧 run 保持终态；历史显示当时事实和当前处理状态 |
| 一个决定等待，其他岗位仍有工作 | 仅依赖动作暂停，其余继续；整轮可结束，未解决事项保留 |
| 明确批准后平台不可用 | 退出当前待回答列表，后续执行入口仍可见，失败原因明确 |
| 下一轮恢复或上次动作结果不确定 | 先核实授权、条件和实际完成情况，不重复联系或建会 |
| 用户改口或新证据要求重看 | 前后决定可追溯，旧任务不能覆盖新状态，重开有明确原因 |
| 暂缓有日期／无日期、应用期间关闭 | 暂缓可查；到期只恢复提醒，下次打开补上，不自动批准 |
| 岗位明确关闭／仅源文件不可读 | 前者只对受影响事项有据归档；后者保留事项并报异常 |
| 决定已保存，标准更新失败 | 显示资料待同步，下一轮不声称新标准已成功生效 |
| 多动作只有一项完成 | 分别呈现结果，不把整件事误报为全部完成 |
| 读取失败、保存失败、并发旧版本写入 | 不显示虚假零事项或成功，不丢新决定，恢复后可核对处理 |
| 历史旧收据仍为 decision | 无明确处理证据时进入历史待核对；重复引入不重复生成 |
| 后台巡检与主动任务并行 | 阅读位置不跳转，更新提示有来源，记录不串轮、不串工作区 |
| 重点超过首页数量或超出近期窗口 | 首页有明确入口回看完整历史，未解决事项不随窗口消失 |
| 工作流未接入或没有写入结果 | 显示未记录／未接入，不能显示成已确认无变化 |
| 网页窄栏、宽屏、浅深主题与原生 | 信息顺序、事项状态和计数一致，重点与后续入口均可达 |

完成标准：相关模型、读写、服务、工作流接入及分发回归通过；网页实际验证交互与故障展示；原生运行验收若受宿主限制必须明确说明，不能用网页截图代替。

## 11. 遗漏检查结论

产品分支已闭合，没有需要继续让用户选择的业务方向。检查补齐的衔接包括：

- 已决定但未执行的动作也有固定入口，不能在移出待确认后失去跟踪。
- 历史任务的当时事实与关联事项的现在状态同时可查。
- 普通聊天能处理旧事项，不依赖原 run 继续运行。
- 缺记录、读取失败和无变化是不同状态；面板无法读取时不能承诺实时同步。
- 稳定事项身份、并发更新和重试避免重复记录及重复外部动作。
- 任务分类与记录入口必须覆盖实际定时调用；既有真实巡检配置仍待部署阶段核验。

需在实施中决定的是现有模块如何复用、具体字段／命令形态、分页和测试组织，属于实现细节；如发现会改变以上已确认行为的约束，再提出具体冲突。
