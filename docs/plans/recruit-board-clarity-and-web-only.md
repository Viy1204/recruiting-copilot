# 招聘网页看板：信息清晰度与单网页维护方案

日期：2026-11-04

状态：本轮 grilling 的 Q1–Q12 与单网页方向已逐项确认，用户于 2026-11-04 确认完整方案并授权实施与验收。源码实现完成；完整 Node 回归 166/166、网页行为与部署回归 26/26、多视口浏览器验收通过。工作区注册 Shell 测试受本机 Windows 符号链接权限限制未通过，详见[验收记录](../../verification/board-web-only-checks.md)。未部署真实工作区、未提交或发布。

## 1. 目标与依据

让用户可以直接识别每条进展和事项涉及的人选、岗位、事件及待决定的问题；历史任务使用可读名称；岗位筛选结果与标签含义一致。各 Agent 共用同一网页看板，移除 Claude 原生看板的独立维护负担。

本次沿用 [ADR 0001](../adr/0001-cross-round-decisions.md) 的跨轮事项、决定与执行分离、聊天决策入口和来源追溯规则，沿用 [ADR 0002](../adr/0002-board-progressive-disclosure.md) 的总览／岗位与人选／执行记录三个视图、渐进展开和阅读位置保护。实施时新增 ADR，明确单网页交付及原生退役，更新上述决策涉及原生交付与验收的条款；保留其历史记录。

问题已从当前工作树核实：

- 近期进展主要使用自由文本，缺少稳定的对象展示和事件细节结构。
- 任务选择器只要遇到相同任务名称及岗位，就追加完整任务 ID，即使创建时间已不同。
- 历史事项保留来源轮次及结果引用，但页面未利用这些引用展示人岗关联。
- “在招”排除部分非在招状态，却仍包含未知状态；关注选择器始终读取全部岗位，容易与外层筛选混淆。
- 原生看板有独立插件入口、注册代码和宿主专用测试，同时复用网页所需的模型及部分脚本，不能整包删除。

这里只核查了源码。真实工作区的岗位状态、旧记录可恢复比例及已安装的原生副本未核实。

## 2. 已确认的设计树

```text
招聘网页看板
├─ 总览与近期进展
│  ├─ 人选、岗位、进展优先，细节与更新时间分层（Q1）
│  ├─ 桌面两栏各自按内容定高，窄屏上下排列（Q5）
│  └─ 新记录提供结构化信息，旧记录按可靠信息降级（Q10）
├─ 历史任务
│  └─ 类型、时间、对象组成可读名称，完整 ID 收入详情（Q2）
├─ 跨轮事项
│  ├─ 对象、岗位、问题、必要背景、依据入口齐备（Q3）
│  ├─ 全部事项按岗位分组，保留状态筛选（Q6）
│  ├─ 来源可恢复则补充，无法关联则明确提示（Q8）
│  ├─ 事项／进展详情连接资料，支持逐层返回（Q9）
│  └─ 岗位组与组内事项按处理优先级排序（Q11）
├─ 岗位范围与关注
│  ├─ 在招严格按状态，全部保留历史，关注为个人集合（Q4）
│  ├─ 切范围后保留有效选择，清除范围外选择（Q7）
│  └─ 未知状态有可点击提示，相同范围有解释（Q12）
└─ 单网页维护
   ├─ 所有 Agent 使用同一网页入口（用户补充）
   ├─ 清理原生界面、独立注册入口及专用验证
   └─ 保留共享协议、网页服务、工作流记录能力与安装过渡说明
```

## 3. 页面与交互方案

### 3.1 总览与近期进展

总览保留紧凑的最近任务条、最多三条待处理摘要和最近七天最多三条近期进展。超过三条的近期进展保留完整列表入口，更早的记录仍可从执行记录回看。

桌面下，“待回答／待核对”和“近期进展”是两个分别按内容确定高度的区块，不再被同一个大框强制撑成等高。标题、内容边界、行间距与入口位置统一；只有一条进展时只占对应内容所需的高度。窄屏纵向排列。

近期进展采用紧凑事件列表：

1. 主信息：相关人选或对象，以及发生的进展。
2. 次信息：所属岗位。
3. 事件细节：只展示与此类事件相关、且已核实的信息。例如面试预约展示预约时段和面试官。
4. 辅助信息：明确标注更新时间，详情入口与当前条目相邻。

预约时间、事件发生时间和记录更新时间分别表达，不能互相替代。工作区级事件无需硬套人选或岗位。视觉延续浅底、细边框、克制强调色，用排版层次改善精致度。

### 3.2 工作区任务名称

任务选择器使用“任务类型 · 创建时间 · 相关对象”的名称。相关对象优先使用已核实的岗位或人选；跨岗位任务可以显示已知的岗位数量。无可靠对象信息时省略该段。

- 时间已能区分的同类任务，不再追加 ID。
- 同一分钟且可读名称仍相同的任务，用简短序号区分；序号只用于展示，不改变任务身份。
- 完整任务 ID 保留在详情与诊断信息中，内部选取、链接和来源引用仍使用原 ID。
- 保持实时跟随、手动固定历史任务和阅读时不被新任务抢占的行为。

### 3.3 待回答／待核对事项

每条摘要应让用户直接理解：关于谁、哪个岗位、要决定什么、为什么需要决定。列表提供对象与岗位、问题、一句必要背景、状态和详情入口；资料与依据可从详情继续查看。

总览仍只显示最多三条摘要。存在当前待回答事项时优先展示；没有当前待回答而有历史待核对时展示待核对摘要。历史待核对保持其历史性质，不自动认定仍需执行。

“全部事项”按岗位分组，保留待回答、历史待核对、已暂缓、后续执行、处理历史及全部状态的筛选。岗位组标题显示岗位名和当前列表中的事项数；工作区总数保持原有统计口径，不被岗位浏览或任务选择改变。

默认处理顺序：

1. 当前有效待办中，已逾期、到提醒时间或明确阻塞下一步的事项。
2. 其他当前待回答事项。
3. 历史待核对事项。

已暂缓、后续执行和处理历史保留各自入口，在“全部”中也可查看。岗位组按当前筛选结果中最高处理优先级的事项排序，组内遵循相同规则；同等优先级按等待时间从早到晚排列，保持稳定。只有真实截止时间和提醒时间才能产生到期判断，历史导入时间不构成新的紧急性。

### 3.4 历史关联与缺失信息

优先利用已有明确关联恢复展示信息：来源同时提供轮次和结果引用，且结果存在并通过校验时，可从规范的 `candidateId` 取得记录中的姓名和原岗位；当前标准岗位可按已有有效台账及别名映射归组，原岗位信息继续可查。

| 情况 | 呈现方式 |
|---|---|
| 来源可靠，能定位人选与岗位 | 展示人选、岗位和原有背景，提供可用的资料入口 |
| 岗位已关闭或人选不在当前台账 | 保留原记录的人岗信息；当前资料不可用时明确提示 |
| 只能确定部分信息或存在歧义 | 展示已确定部分，标记“关联待确认”；未确定岗位的事项归入“岗位待确认” |
| 明确属于整个工作区的事项 | 归入“工作区事项”，与信息缺失分开 |
| 来源记录缺失或读取失败 | 保留事项及可用内容，明确说明来源不可用，不把缺失当作无事项 |

不凭自由文本中的姓名自动绑定岗位，不因同名合并不同原岗位的人选记录。已有来源可能涉及多个对象时，保留已核实关联，不任意挑选其中一个作为唯一对象。

历史补充首先是读取与展示层的关联，不重写旧任务事实，也不把历史事项自动改为已解决。新字段采用向后兼容方式加入，旧文件不要求先批量迁移才可打开。

### 3.5 详情与返回路径

点击事项或进展先进入这件事的详情，首屏顺序为：对象与岗位 → 发生的进展或待决定的问题 → 必要背景 → 当前状态。人选资料、相关事项和来源记录有明确入口；完整证据与修改历史默认收起。

支持“进展 → 关联事项 → 人选资料”的逐层返回。返回恢复前一层内容、列表位置和筛选；关闭恢复初始触发位置及焦点，Esc 退出行为与现有详情交互保持一致。复用页面已有面板与资料能力，不叠多层弹窗。

### 3.6 岗位范围与个人关注

| 入口 | 确认后的含义 |
|---|---|
| 在招 | 只包含明确标为“在招”的岗位 |
| 全部 | 包含全部岗位，明确显示在招、暂停、已关闭、已下架、待核及未知状态 |
| 我的关注 | 本机、按工作区隔离的个人岗位集合，可包含任意招聘状态；关注不修改招聘状态 |

“选择关注”放入独立面板，清楚说明正在编辑个人关注名单。其来源是全部岗位，不受外层范围限制，但不再嵌在筛选结果内造成混淆。

切换范围时：原岗位仍属于新范围就保留；否则清除岗位选择，回到新范围汇总，并给简短提示。候选阶段和人数随新范围一致更新。

未知状态默认不进入“在招”。存在未知岗位时，在范围附近显示“另有 N 个岗位状态待确认”，点击进入“全部”并定位相应岗位；沿用现有岗位管理能力处理可编辑岗位。只在台账出现、尚未配置的岗位明确说明来源，不假定已有可写岗位行。

当已成功读取且确实全部岗位均在招时，“在招”和“全部”内容相同是正确结果，用数量与“当前全部岗位均在招”的简短说明解释。空关注集合提供选择入口；读取失败、未知数量及真实空集合分别表达。

## 4. 新记录与兼容约束

后续工作流在记录已核实进展时，同时提供可展示的对象关联、岗位与事件细节。面试预约按需提供预约时段及面试官，其他类型只记录其相关信息。具体字段和校验实现由编码阶段确定，业务要求是：信息有明确来源，缺失有正常降级，额外字段不破坏既有任务与事项记录。

同步更新初始化、岗位梳理、每日招聘、简历评估、面试预约、人才盘点六个工作流的记录说明与共享参考；主动任务与定时任务使用同一记录约定。旧版工作流写出的旧格式仍可读取。

旧进展只拆分可以可靠确定的信息；无法结构化的原文保留在详情中。不把未验证的计划写成成功结果，也不让一次无变化巡检覆盖先前仍有价值的进展。

共享数据继续以工作区本地文件为准，保留跨轮事项身份、版本校验、来源追溯、原子写入与失败缓存机制。决定与执行分别记录，聊天继续是决策入口。

## 5. 原生看板退役范围

实施时清理原生专用内容，并以引用关系为依据确认边界：

- 原生界面与会话注册：`skills/recruit-board/hooks/register.tsx`、对应 `hooks.json`。
- 独立原生插件：`skills/recruit-board/.claude-plugin/plugin.json` 及根 marketplace 中的 `recruiting-board` 项；保留主招聘插件与网页 Skill。
- 原生宿主专用测试、类型扩展、验收配置和预览同步脚本；共享类型和公共行为测试继续保留。
- 技能说明、安装使用入口、当前设计说明中“原生面板可选”的指引，以及依赖宿主原生引擎的验收要求。

保留网页 `public/`、服务与连接脚本、共享模型、资料读取、岗位管理、任务／结果／事项记录协议和六个工作流接入。`actions.mjs`、类型文件及其他共用文件先查引用，不能因原生界面使用它们就整份删除。

新增 ADR 记录单网页维护决定，并更新现行文档。过往 ADR、方案和发行记录作为历史保留，对已被替代的当前指引加清楚的后续说明。

删除源码入口不会卸载用户电脑或其他工作区中已安装的原生副本。本次提供升级与停用说明；不自动删除未知安装位置。跨 Agent 的网页使用继续按宿主实际能力打开或复用本机页面，缺少打开能力时提供完整本机链接。

## 6. 实施组织与范围

在当前功能分支推进，保留已有未提交改动。建议按依赖顺序实施：

1. 补充向后兼容的展示数据与可靠关联读取，覆盖历史来源缺失和同名不同岗位等边界。
2. 调整总览、事项列表与详情导航，再更新任务名称、岗位筛选和关注面板。
3. 同步工作流写入约定与文档，清理原生专用入口和依赖，新增 ADR。
4. 运行公共行为回归、完整 Node 测试及网页交互验收，修复问题并交付差异和验证证据。

预计涉及 `skills/recruit-board/` 的模型、类型、记录脚本、网页及参考说明，六个工作流 Skill、主插件 marketplace、相关测试和设计文档。具体文件以实施时的引用核查结果为准。

本次交付范围是源码／模板仓库及隔离的虚构工作区验收。真实工作区安装副本的升级、真实历史数据的核实或修复、提交、推送和发布不包含在本轮方案确认中。

## 7. 验收标准

所有数据用隔离的虚构工作区构造，不把真实岗位、人选或截图中的个人信息加入源码及测试。

| 编号 | 场景 | 通过标准 |
|---|---|---|
| A1 | 左栏三条事项、右栏一条进展 | 两个区块分别按内容定高；进展没有被强制撑高的空白框，入口紧邻对应条目 |
| A2 | 新版面试进展及其他事件 | 人选／对象、岗位、进展、相关细节层级清楚；预约时间与更新时间不混用；非面试事件无无关占位字段 |
| A3 | 旧版自由文本进展、超过三条进展、无变化巡检 | 无可靠结构信息时正常降级并保留原文；完整近期列表可达；无变化任务不抹掉旧进展 |
| A4 | 同类任务时间不同、同分钟重名、手动固定历史任务 | 列表无完整 UUID；真正同名时用简短序号区分；仍能选中正确任务，详情保留原 ID，阅读不被抢占 |
| A5 | 历史事项有合法结果引用 | 正确显示原人选与岗位及必要背景；原岗位关闭或人选离开当前台账后仍能理解历史事项 |
| A6 | 同名不同岗位、缺失结果、关联歧义、工作区级事项 | 不串人串岗；缺失明确提示；“岗位待确认”和“工作区事项”分开；不自动改变事项状态 |
| A7 | 多岗位、多状态事项混合 | 全部事项按岗位分组，组标题和数量正确；状态筛选不丢记录，工作区总数口径保持一致 |
| A8 | 紧急当前待办、普通待回答、历史导入、已暂缓事项 | 岗位组及组内顺序符合优先级；同级较早事项在前；导入时间不制造紧急性，无真实期限不显示逾期 |
| A9 | 进展进入事项，再进入资料并返回／关闭 | 逐层返回内容正确；列表滚动、筛选和焦点恢复；缺失资料有明确反馈，不产生多层叠加弹窗 |
| A10 | 在招、暂停、关闭、下架、待核及未知岗位混合 | “在招”只含明确在招岗位；“全部”完整保留各状态；候选阶段和人数与范围一致 |
| A11 | 已选岗位在／不在切换后的范围内 | 范围内保留选择；范围外清除并回到新范围汇总，有简短提示 |
| A12 | 跨状态关注、空关注、切换工作区 | 关注可选所有状态；选择器独立呈现；关注不改招聘状态，不跨工作区泄漏，本机刷新后偏好仍在 |
| A13 | 存在未知岗位、全部确实在招、空岗位、配置读取失败 | 未知提示的数量和跳转正确；确实相同时有解释；空或失败不误报“全部均在招”，错误不伪装为零 |
| A14 | 新旧记录混合、来源失败、陈旧缓存、事件更正 | 旧文件可读，新字段按入口校验；保留最后可信内容与来源；更正可查，任务和事项身份不变 |
| A15 | 原生退役后的安装包、入口与测试 | 无原生独立注册入口及宿主专用依赖要求；主招聘插件、网页连接、数据记录和读取正常，相关安装回归通过 |
| A16 | 网页完整操作与多视口 | 在 320、375、768、1280px 及更宽桌面验证浅／深主题；长姓名和岗位不遮挡操作；键盘可用，无本次变更造成的控制台或网络错误 |

验证包括：针对行为变化的模型／记录／安装回归，以及 `npm test`；原生专用测试移除后，公共行为继续由不依赖原生宿主的测试覆盖。浏览器实际点击、筛选、逐层返回、主题及响应式验收使用 Preview 工具，交付截图和相关测试结果。只有静态阅读或单元测试通过不等于页面已验收。

## 8. 整体确认

Q1–Q12 与单网页方向已逐项确定。用户确认本文与预期一致后，按以上范围实施并验收；若调整的是局部条款，只重开受该条款影响的设计分支。
