# 招聘看板：处理结果、岗位归并与资料入口修复方案

日期：2026-11-04

状态：用户已确认实施，包含真实工作区升级和历史资料补齐；以打开或下载原件为准，不要求看板内预览。

## 目标与交付范围

解决用户正在使用的看板中四类问题：执行记录重复、名单入口缺少反馈、历史岗位名称无法管理、已有候选资料无法打开。

交付包括源码修复、虚构工作区验证，以及备份后升级真实招聘工作区、归并指定岗位和补齐历史资料。真实岗位、候选人和资料只在招聘工作区处理；本文件只记录通用规则和经确认的交付范围，不写入个人资料或私人路径。

文件可用的完成标准是“能从候选详情打开对应文件或下载原件”。不要求内嵌 PDF、图片或办公文档预览，不引入文档转换流程。

## 已核实的原因及验证限度

| 用户所见 | 已核实原因 | 尚待实施阶段验证 |
|---|---|---|
| 本轮重点、近期流水内容相近 | 两块分别读取 highlights 与 results，没有跨来源归并；一个评价可同时写入两者 | 指定任务的具体重复事件与浏览器实际效果 |
| 查看名单、确认记录似乎没有反应 | 两按钮展开同一个位于下方的处理列表，未聚焦或滚动到目标；0 确认仍展示按钮 | 用户现场是目标在屏下、请求失败，还是其他运行状态问题 |

磁盘中的主要部署文件与源码一致；当前浏览器运行的服务实例和实际加载资源尚未核验。访谈阶段仅做只读调查，没有修改代码或真实工作区，没有执行测试，也未补取外部资料。

## 已确定的设计树

```text
执行记录
├─ 一份按人选组织的结果列表
│  ├─ 默认：最新结论、下一步
│  ├─ 展开：该人本轮完整处理经过与证据
│  └─ 缺乏可靠人选关联的记录：单列并解释
├─ 处理名单入口：打开真实列表并定位
└─ 确认入口
   ├─ 先看该轮关联且当前仍需回答的事项
   ├─ 已确认、暂缓及旧收据进入历史区
   └─ 已知为零：文字说明；读取失败、未记录另行说明

岗位管理
├─ 正式岗位：管理其招聘状态
└─ 仅见于台账的名称：管理入口内待归并
   ├─ 关联已有正式岗位，沿用其状态
   └─ 保留原始台账与身份，不凭名称猜测合并

候选资料
├─ 已确认的外部文件：复制到工作区，保留来源及原件
├─ 关联明确：补齐档案、brief、原始简历等各类资料
├─ 关联歧义：候选详情选择并确认，持久保存
├─ 已有历史：覆盖全部台账，推进中人选优先
├─ 原简历缺失：沿已记录来源只读补取
└─ 文件入口：打开或下载原件，不要求看板内预览

交付
├─ 源码与虚构数据验证
└─ 备份后部署真实工作区并核验
```

## 1. 执行记录只保留一份人选结果

采用 Q1、Q3 的选择，将“本轮重点”“近期流水”和完整处理名单组织成一份按人选阅读的结果列表。一个可靠的人选身份在同一轮只占一个条目；默认给最新有效结论及有记录的下一步，展开查看完整处理经过、证据和来源。没有记录下一步时不编造。

分组沿用原人岗身份，即 `runId + candidateId`，同名异岗不自动合并。读取完整 results，不能用最近三条流水代替完整经过。重点和结果只有可靠对象关联时才进入同一人条目；没有可靠关联的旧重点，以及岗位／工作区事件另行保留，不根据相似文本或时间接近强行绑定。

合并是阅读结构调整，原收据、重点、事件时间、更正历史及来源继续保留。确属同一事件的重复摘要不重复铺开；同一人不同事件保留在处理经过中。总览仍可显示近期有用进展，点击进入对应任务和人选结果。

“处理人选 N 人”打开真实结果列表并把目标带到可见位置，提供正确焦点和返回行为。人数由实际分组结果计算，读取失败、未记录与空列表分别表达。

## 2. 确认入口表达当前状态

采用 Q6，将所选任务关联事项中当前仍需用户回答的内容放在前面；已确认、暂缓、后续执行和历史收据保留在同一详情能力的历史区，不再次铺成重复摘要。

入口数字使用当前关联事项的状态，单位为“项”，不再把旧收据里曾经标记 `attention=decision` 的人数当成现在待回答数。已知没有待回答时显示“本轮暂无待回答事项”等文字，不保留零数量按钮；这不等于整个工作区没有待办。

旧收据无法可靠关联当前事项时保留其历史性质及待核对提示。读取失败或状态未知不能显示成零。确认和实际执行继续分离，保持聊天为决定入口，不增加网页批准或平台操作。

## 3. 历史岗位可以从管理入口归并

采用 Q5，管理岗位同时展示正式岗位与仅见于台账的待归并名称。待归并条目允许关联到已有正式岗位，沿用其招聘状态，并明确说明归并结果。未确定的仍保留待归并状态，不自动改成在招或新建正式岗位。

采用 Q8，对已核实并经用户确认的历史写法，主归属统一到对应正式岗位；已确认的兼评方向留在对应人选详情。具体岗位映射只写入用户工作区，不把任意组合岗位自动拆分或归入一边。

保留台账原岗位、去重键和历史来源；岗位别名改变展示与筛选，不制造或删除候选记录。若真实工作区的现有说明与本次确认个例冲突，仅同步相关规则，保留历史依据。

## 4. 资料关联、归档与文件入口

### 归档与后续流程

采用 Q2，已确认属于候选人的工作区外简历及相关材料复制归档到招聘工作区。保留原文件和来源，用内容校验避免同一资料重复导入或同名覆盖。复用现有 `runtime/resumes/` 目录和内容去重约定；本地文件导入不伪造邮件 ID。

后续收取、评估及建档流程同步写入可靠资料关联。不能只在看板端补救，随后继续产生空路径或外部缓存引用。

### 全量历史补齐

采用 Q4，覆盖全部台账，先处理面试、Offer 等正在推进的人选，再处理其余历史人选。只使用已有引用、档案、索引及可核实来源，不扫全盘猜附件。

已有档案和 brief 应分别作为对应类别展示；它们不能替代原始简历。面试阶段不会自动证明任意同名文件归属，但也不应因描述字段的格式差异把已有可靠关联隐藏掉。

采用 Q7，明确身份的资料自动补齐；打码姓名、同名异岗、多份资料等歧义在候选详情提供“关联资料”入口。用户选择和确认后持久保存关联，并允许更正错误关联。候选详情必须先给实际可用文件，再说明仍缺什么。

采用 Q9，原始简历没有可靠路径时，沿已记录的收取来源只读查找或补取，包括必要的来源邮件／招聘平台会话。此授权不包括发消息、索要简历、拒绝候选人或其他平台动作。仍无法获取时明确区分“原始简历未获取”与“档案已可查看”，不宣称文件不存在。

### 文件打开方式：以最后补充为准

Q10 中对格式覆盖的目标保留，“看板内预览”和“本地转换”要求由用户最后补充取消：

- PDF、PNG/JPG：提供明确的打开入口，以新标签页交给浏览器查看，同时可下载原件。
- Markdown、TXT：保留现有可读能力，并提供打开或下载入口。
- DOC、DOCX、RTF：提供原件下载，由本机相应应用打开；不为此次修复增加转换服务。
- 文件缺失、关联待核对、文件无法读取分别说明，不把所有问题都归成“台账未填写路径”。已有关联且能打开的资料不再被通用提示遮盖。

文件通过本机服务的候选资料资源入口访问，不依赖网页直接跳转 `file://`，不开放任意磁盘路径。已归档原件的身份与来源可追溯。

## 5. 实施顺序与验证

1. 复现执行记录与两个按钮的当前行为，核对真实看板服务实例与资源来源，区分已证实缺口和现场根因。
2. 修改源码中的结果呈现与导航、当前确认事项入口、待归并岗位管理、资料关联和原件打开能力；同步必要工作流约定及 ADR。
3. 用隔离虚构工作区验证公共行为与浏览器交互，不把真实资料放进源码仓库或验收截图。
4. 备份真实工作区相关界面、配置和将修改的索引，升级看板并写入已确认岗位映射。
5. 按优先顺序补齐历史资料、验证复制结果和打开入口，最后核验真实看板。缺失或歧义材料形成明确待补清单，不冒充完成。

验收至少包括：

- 同一人简历评价不会在相邻两个区块重复显示；处理经过完整，同名异岗不误并，无人选关联的记录不丢失。
- 从总览最近记录进入正确任务；处理名单点击后目标立即可见；1 人、0 项、请求失败及旧记录场景均有正确反馈。
- 当前待回答与旧确认收据的数量、状态、历史访问互相一致。
- 待归并名称能从管理入口处理，指定 UE 旧名称归入正式在招岗，原始身份及兼评方向保留。
- 已有面试档案和 brief 可打开；原简历缺失如实提示；打码及同名资料需确认后关联，保存后重启仍有效。
- 外部截图复制校验后可从候选详情打开；PDF 可在新标签页读取；办公文档可下载原件；原文件未覆盖或删除。
- 历史补齐可重复执行，不重复导入或挂错文件；对失败、歧义和缺失提供逐项结果。
- 相关 Node 测试和实际浏览器点击通过；布局变动检查窄屏、桌面与浅深主题，真实部署再核验。
